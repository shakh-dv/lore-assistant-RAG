# Lore Assistant — техническая опись проекта

Документ описывает, что **реально** написано в проекте. Каждое утверждение
проверено по коду или SELECT-запросом к живой базе; рядом стоит путь к файлу.

Если что-то не реализовано — об этом сказано прямо, а не пропущено.

---

## 1. Что это

Чат, который отвечает на вопросы по загруженным текстам («лору»), опираясь
только на то, что лежит в базе. Пользователь пишет вопрос, система находит
похожие куски текста через векторный поиск и отдаёт их языковой модели вместе
с вопросом. Модель формулирует ответ по найденному, а не по своим знаниям.

Это классический **RAG** — Retrieval-Augmented Generation, генерация с опорой
на поиск.

## 3. Архитектура: порты и адаптеры

Проект построен по **гексагональной архитектуре** (она же «порты и адаптеры»,
она же чистая архитектура). Смысл: бизнес-логика не знает, откуда берутся данные
и какая модель отвечает. Заменить Postgres на другое хранилище или Gemini на
OpenAI можно, не трогая логику.

### Слои

```
app/
├── domain/           ← ядро: интерфейсы, понятия, чистые трансформации
│   ├── ports.py           IVectorStore, ILLMClient
│   ├── answer_modes.py    AnswerMode: рассказчик / архивариус
│   └── wiki_chunker.py    chunk_article() — wikitext -> список чанков.
│                          Ни БД, ни сети, ни диска — чистая функция dict -> list[dict]
│
├── use_cases/        ← бизнес-логика. Знает только про domain
│   ├── chat.py           ChatUseCase — оркестрация RAG
│   └── universes.py      ListUniversesUseCase
│
├── infrastructure/   ← реализации портов. Знает про SQLAlchemy и Gemini
│   ├── postgres_adapter.py   PostgresVectorStore
│   ├── gemini_adapter.py     GeminiAdapter
│   └── database/             модели, подключение, Alembic-миграции
│
└── api/              ← composition root: здесь всё склеивается
    ├── dependencies.py   создаёт адаптеры и передаёт в use case
    ├── router.py         HTTP-эндпоинты
    └── schemas.py        pydantic-схемы запросов и ответов
```

**Вне `app/`, на верхнем уровне репозитория** — отдельная группа top-level
скриптов: `fandom_scraper.py` (скрейпер), `index_fandom.py` (индексатор),
`load_gts.py` (разовый загрузчик вселенной GTS),
`rebuild_lexicon.py`, и пакет `eval/` (контрольные вопросы + раннер,
раздел 5.5). Они не часть живого API — не импортируются `main.py` и
не участвуют в обработке HTTP-запросов, но переиспользуют те же порты и
адаптеры (`GeminiAdapter`, `PostgresVectorStore`), что и веб-приложение.
Разобраны отдельно в разделе 5.

### Правило направления зависимостей

Всё смотрит **внутрь**, к домену. Проверяется одной командой:

```bash
grep -rn "infrastructure" app/use_cases/    # должно быть пусто
grep -rn "use_cases" app/infrastructure/    # должно быть пусто
```

Обе команды не находят ничего — правило соблюдено.
`app/domain/ports.py` импортирует только `typing` и соседний модуль домена.
`app/domain/wiki_chunker.py` импортирует только `re`, `typing` и внешний
`mwparserfromhell` — тоже ничего из `infrastructure`/`use_cases`.

### Порт → адаптер

| Порт (`domain/ports.py`) | Адаптер | Где создаётся |
|---|---|---|
| `IVectorStore` | `PostgresVectorStore` | `api/dependencies.py`, `get_vector_store` |
| `ILLMClient` | `GeminiAdapter` | `api/dependencies.py`, `get_llm_client` |

Порты описаны через `typing.Protocol` — это «утиная типизация» со статической
проверкой: классу не нужно наследоваться от интерфейса, достаточно совпадения
методов.

`get_llm_client` помечен `@lru_cache(maxsize=1)`: адаптер без состояния, а внутри
него `genai.Client` держит пул HTTP-соединений. Без кэша клиент создавался бы
заново на каждый запрос, и соединения не переиспользовались бы.

### Транзакции

`get_async_session` в [`app/infrastructure/database/connection.py`](../app/infrastructure/database/connection.py) —
это зависимость FastAPI с `yield`: при исключении делает `rollback`, в `finally`
всегда `close`. **Явного `commit` там нет** — и это правильно: путь чата только
читающий. Скрипты загрузки коммитят сами, `index_fandom.py` — по одной статье
за раз (раздел 5), остальные — одной транзакцией на весь документ.

## 4. Путь запроса: от клика до буквы на экране

1. **Фронт** собирает тело запроса — вопрос, вселенная, режим ответа и последние
   6 сообщений истории. `static/index.html`, функция `ask()`.
2. **FastAPI** валидирует его схемой `ChatRequest` (`api/schemas.py`).
   Неизвестный режим отсекается здесь же — ответ 422.
3. **DI** собирает `ChatUseCase`: сессия БД → `PostgresVectorStore`,
   закэшированный `GeminiAdapter` (`api/dependencies.py`).
4. **`ChatUseCase.execute`** ([`app/use_cases/chat.py:39`](../app/use_cases/chat.py)) —
   весь RAG, разобран в разделе 7.
5. **`StreamingResponse`** отдаёт асинхронный генератор
   ([`api/router.py:52`](../app/api/router.py)).
6. **Фронт** читает поток через `res.body.getReader()` и печатает текст
   по времени, с постоянной скоростью.

## 5. Путь загрузки: от Fandom до вектора в БД

Этого раздела не было в первой версии документа — весь пайплайн написан позже.
Разбит на четыре слоя, в порядке прохождения данных.

### 5.1 `FandomScraper` ([`fandom_scraper.py`](../fandom_scraper.py)) — сырые данные с вики

Тонкая обёртка над MediaWiki API `assassinscreed.fandom.com/ru/api.php`. Никакого
парсинга HTML — `action=query`/`action=parse` отдают уже структурированные данные.

- **Rate limit** — 1 запрос/сек, реализован через `asyncio.Lock` + `time.monotonic()`
  ([`fandom_scraper.py:86-124`](../fandom_scraper.py)). Лок нужен даже без параллельных
  вызовов сейчас — защита на будущее, если кто-то решит дёрнуть `fetch_article`
  параллельно.
- **`maxlag=5`** в каждом запросе — конвенция MediaWiki: если реплика БД отстаёт
  больше чем на 5с, сервер сам просит подождать, вместо отдачи рассинхронизированных
  данных.
- **Ретраи с backoff** (`min(2**attempt, 30)`, до 5 попыток) — только для того, что
  реально может пройти при повторе: сетевые сбои, 5xx/429, `maxlag`/`ratelimited` в
  теле ответа. `missingtitle`/`invalidtitle`/`nosuchpageid` — свойство конкретной
  статьи, не ретраится, `fetch_article` возвращает `None`.
- **`redirects=1`** ([`fandom_scraper.py:179`](../fandom_scraper.py)) — без этого параметра
  запрос на статью-редирект (например «Эцио Аудиторе» → «Эцио Аудиторе да Фиренце»)
  отдаёт текст самого редиректа (`#перенаправление [[...]]`, десятки символов), а не
  статью-цель. Найдено эмпирически: `--title "Эцио Аудиторе"` до фикса давал 1 чанк
  вместо 37.
- **`byteoffset` у `sections`** — по документации MediaWiki это смещение в БАЙТАХ
  UTF-8-текста. На практике, проверено на реальной статье «Альтаир ибн Ла-Ахад»
  (4 секции подряд): байтовый срез даёт битые символы (`�`), посимвольный —
  чисто совпадает с началом заголовка секции. У этой инсталляции Fandom
  `byteoffset` фактически ведёт себя как индекс символов python-строки. Использован
  посимвольный срез — расхождение с документацией не переносить на другие вики без
  повторной проверки.

`fetch_article` одним вызовом `action=parse` забирает сразу `wikitext`, `sections`,
`categories`, `revid` — экономнее для rate limit, чем четыре отдельных запроса.

### 5.2 `chunk_article()` ([`app/domain/wiki_chunker.py`](../app/domain/wiki_chunker.py)) — wikitext в чанки

**Почему structure-aware chunking, а не альтернативы.** Обоснование по
бенчмаркам 2025-2026, а не на глаз:

- Weaviate (2025): разница между лучшей и худшей стратегией чанкинга на одном
  корпусе — до 9% recall.
- Vectara / NAACL 2025 (arXiv:2410.13070): чанкинг влияет на качество не
  меньше, чем выбор embedding-модели.
- FloTorch (2026): слишком мелкие чанки (~43 токена) дают высокий retrieval
  recall, но end-to-end accuracy падает до 54% — LLM получает недостаточно
  контекста.
- Chroma, «context rot» (июль 2025): деградация качества уже около 2500
  токенов контекста — значит, чанк не должен быть ни слишком мелким (ломает
  смысл), ни слишком крупным (разбавляет релевантный кусок мусором в
  контекстном окне).

Три альтернативы и почему они хуже для вики-текста Fandom:

- *Fixed-size (по 512 токенов подряд)* — теряется вики-структура, разрывает
  секции пополам. Вопрос «какое оружие у Эцио» ловит чанк с половиной текста
  про детство.
- *Semantic chunking по embedding similarity* — дорого (лишние вызовы Gemini
  API на каждую границу), и на конечное качество ответа проигрывает
  структурному подходу, когда структура уже есть в исходнике (вики размечена
  секциями `==H2==`/`===H3===`).
- *Hierarchical parent-child (auto-merging)* — лучший результат по ARAGOG
  2024, но сложнее: два уровня чанков, merging при retrieval. Отложено —
  задел под него в схеме (`parent_chunk_id NULLABLE`, раздел 6) есть, но не
  заполняется; фактическая реализация ниже проще (merge коротких секций
  назад, в плоский список, не в дерево).

Реализация:

1. **Инфобокс, отдельно от секций, на полном wikitext.** `mwparserfromhell.parse(...)
   .filter_templates(recursive=False)`. Классификация «это инфобокс»: сначала по
   имени шаблона (`{"инфобокс", "infobox", "персонаж", "предмет"}` в
   `template.name.strip().lower()`), иначе — по количеству именованных параметров
   (`≥3`, и больше половины с `showkey=True`) — вторая проверка отсекает
   навигационные шаблоны вида `{{Игровая_серия|AC1|AC2|AC3}}`, у которых все
   параметры позиционные. Сериализуется в `"Ключ: значение. Ключ2: значение2."`.
2. **Плоский список секций по byteoffset** (посимвольно, см. 5.1). Lead — текст до
   первого `==Заголовок==`, отдельная псевдо-секция `toclevel=0`. `section_path`
   строится через стек `(toclevel, title)` — родитель содержит только свой
   вступительный текст до первого подраздела, не текст детей.
3. **Очистка** (`_clean_wikitext`) — `<ref>`/комментарии убираются целиком (с
   содержимым), файловые вики-ссылки (`[[Файл:...]]`) — тоже целиком (их «текст»
   после `strip_code()` это layout-мусор типа `thumb|250px|left`, не проза).
   `<tabber>` (вкладки с диалоговыми ветками) — свой мини-синтаксис поверх
   `strip_code()`: `|-|`-разделитель вырезается, `Label=` превращается в `Label:`
   (не теряет информацию о том, какая это ветка диалога).
4. **Merge коротких секций — назад**, в уже принятый предыдущий чанк, не вперёд.
   Обоснование: подраздел обычно продолжает тему предыдущего
   (`Биография → Юность → Тренировки` — слить «Тренировки» с «Юность» сохраняет
   тему, слить со следующим «Снаряжение» рвёт её). Упрощение относительно
   исходного плана (иерархический merge в дерево секций) — сознательное, ради
   меньшей сложности без потери качества.
5. **Рекурсивный сплиттер** для секций длиннее порога — каскад разделителей
   `["\n\n", "\n", ". ", " "]`. Overlap — не сырой срез по символам, а поиск
   ближайшей границы (`\n` или `. `) в пределах небольшого окна, чтобы не резать
   посередине слова.
6. **Префикс `section_path` — внутри `chunk_text`, не отдельным полем.**
   `ChatUseCase` склеивает контекст для LLM буквально из `chunk_text` без
   обогащения на лету (раздел 7, шаг 5) — без префикса модель не увидит, из
   какого раздела статьи кусок.

**Токены считаются эвристикой** — `CHARS_PER_TOKEN = 3.0`, не точным подсчётом.
`tiktoken`/`sentencepiece` в проекте нет: `count_tokens` Gemini — сетевой вызов,
неприемлемо дёргать на каждой границе чанка на тысячах статей.

### 5.3 Устойчивость `GeminiAdapter` к лимитам Gemini ([`app/infrastructure/gemini_adapter.py`](../app/infrastructure/gemini_adapter.py))

Написана целиком по следам реальных сбоев на живом прогоне, не заранее.
У Gemini free tier — **два независимых предела** на `embed_content`:

| Предел | Значение | Реакция ретраем |
|---|---|---|
| RPM (в минуту) | 100 | Помогает — можно подождать и повторить |
| RPD (в день) | ~1000 | Не помогает — до полуночи по Тихоокеанскому ждать нечем |

Путь одного эмбеддинга (`generate_embedding` для вопроса чата — тонкая обёртка
над тем же кодом, что и батч, [`gemini_adapter.py:168-179`](../app/infrastructure/gemini_adapter.py)):

```
generate_embeddings_batch          — режет список текстов на суб-батчи по ≤80
  -> _embed_sub_batch               — до 5 попыток на суб-батч:
       _throttle_embed_rate         — упреждающая пауза: скользящее окно 60с,
                                       не даёт разогнаться выше 80 текстов/мин
       embed_content                — сам вызов; на 429 смотрим КОД ошибки:
         _has_daily_quota_violation — PerDay -> DailyQuotaExceeded, без ретраев
         иначе (PerMinute/сеть)     — backoff (min(2**attempt, 30)) и повтор
```

**Найденный и починенный баг:** `_EMBED_BATCH_SIZE` (максимум текстов в одном
суб-батче) был **100**, а `_EMBED_RATE_LIMIT_PER_MINUTE` — **80**. Суб-батч
размером 81-100 математически не мог пройти троттлинг: условие
`used + upcoming > 80` истинно при любом `used ≥ 0`, если `upcoming` уже больше
80 само по себе — `_throttle_embed_rate` уходил в бесконечную рекурсию, спя по
60с на каждом витке. Не встретилось на практике (максимум был 37 чанков на
статью), но было вопросом времени на большом корпусе. Исправлено: константы
сравнены (`_EMBED_BATCH_SIZE = 80`), плюс `assert` сразу после определения
обеих ([`gemini_adapter.py:98-102`](../app/infrastructure/gemini_adapter.py)) —
инвариант, не рантайм-проверка: если кто-то снова их раздвинет, падение будет
сразу при импорте, а не многочасовым зависанием посреди прогона.

`_has_daily_quota_violation` читает `quotaId` из **структуры** тела ответа
(`error.details[].violations[].quotaId`), не грепает текст ошибки целиком —
один 429-ответ может перечислять сразу несколько нарушенных квот.

**Симметричная защита в `ChatUseCase`** ([`chat.py:73-84`](../app/use_cases/chat.py)):
эмбеддинг вопроса — единственная точка в чате, реально зовущая внешний API перед
стримингом. Обёрнута в `try/except`: при сбое (в том числе дневном лимите) чат
стримит вежливое сообщение, а не падает необработанным traceback в HTTP-ответ.

### 5.4 `index_fandom.py` — оркестрация

Связывает 5.1-5.3 и льёт в БД как `universe='AC'`.

```
uv run python index_fandom.py --dry-run --limit 5      # chunker без LLM/БД
uv run python index_fandom.py --limit 20                 # реальная заливка, малая выборка
uv run python index_fandom.py --title "Эцио Аудиторе"    # точечная переиндексация
uv run python index_fandom.py --title "..." --force      # форс даже при неизменном revid
uv run python index_fandom.py                             # полный корпус
```

- **Инкрементальность по `revid`** ([`index_fandom.py:60-62`](../index_fandom.py)) —
  `revid` статьи сохраняется в `Article.metadata_obj`; при повторном запуске
  статья с неизменившимся `revid` пропускается без обращения к Gemini. Экономит
  квоту на переиндексации, но не экономит сам HTTP-запрос к Fandom — `revid`
  узнаётся ТОЛЬКО из ответа `fetch_article`, значит сходить за статьёй придётся
  в любом случае; экономится дорогое (эмбеддинг + запись в БД), не дешёвое
  (сетевой запрос).
- **Сессия БД и `commit()` — на каждую статью**, не одна на весь прогон
  ([`index_fandom.py:57`](../index_fandom.py)). Падение на статье №800 из тысяч
  не откатывает 799 уже успешно залитых.
- **`DailyQuotaExceeded` ловится отдельно** от прочих исключений
  ([`index_fandom.py:136-147`](../index_fandom.py)) — останавливает весь прогон
  (`break`), а не считается ошибкой одной статьи: после дневного лимита ни одна
  из оставшихся не пройдёт всё равно, ретраить их по одной — часы впустую.
  Любая другая ошибка — лог и переход к следующей статье, прогон не падает
  целиком.
- **`--dry-run`** пишет каждый чанк отдельной строкой в `dry_run_output.jsonl`
  (не только печатает в консоль) — на 20+ статьях/300+ чанках визуально
  скроллить print неудобно, jsonl удобно грепать и агрегировать.

### 5.5 Eval-набор (`eval/`) — измеримое качество

До этого любое «стало лучше/хуже» после правки чанкера, порога или промпта было
на глаз. `eval/` — контрольные вопросы с эталонами и раннер, который прогоняет их
через **продакшен-пайплайн** и выдаёт число. Аналог юнит-тестов для качества
поиска; не мониторинг (тот — про живых пользователей, которых у проекта нет).

- **`eval/dataset.yaml`** — 31 вопрос шести типов: `fact` (точечный факт),
  `narrative` (событие), `relation` (связь двух сущностей), `typo` (намеренная
  опечатка в имени — проверяет `correct_typos`), `followup` (местоимение +
  history — проверяет `rewrite_query`), `out_of_scope` (бот должен отказаться).
  Каждый `expected_fact` сверен с текстом чанка в БД — эталоны описывают корпус,
  а не «правду про AC». Источник — `article_title` как в БД (+ необязательные
  `section_contains`, `chunk_type`), не id чанка: id меняются при переиндексации.
  Факт может быть списком синонимов (`["друг", "друз"]`) — у «друг» и «друзьями»
  общей подстроки нет.
- **`eval/run_eval.py`** — запуск только как модуль (`python -m eval.run_eval`),
  иначе `app` не импортируется. Retrieval-часть повторяет шаги
  `ChatUseCase.execute` явно (опечатки → условный rewrite → эмбеддинг →
  `search_similar`) — `execute` отдаёт наружу только текст, не найденные чанки;
  условие rewrite импортируется оттуда же (`_needs_llm_rewrite`), чтобы не
  разъехаться с продакшеном. `--full` дополнительно получает ответ через сам
  `ChatUseCase.execute` в режиме ARCHIVIST (temperature 0.1, точная фраза отказа).
  `--validate` — схема + наличие каждой эталонной статьи в БД. `--compare A B` —
  таблица дельт по метрикам и списки регрессий/улучшений по каждому вопросу.
- **Метрики.** Retrieval (детерминированы, ~1 embed на вопрос): `recall@5` — эталон
  в top-5; `MRR`; `typo_fixed` — исправилась ли намеренная опечатка;
  `unexpected_correction` («badfix») — вопрос **без** опечатки, который корректор
  всё-таки изменил; `best_distance` — для калибровки порога. Generation (`--full`,
  ~1 generate на вопрос, чат-модель 15/мин на free tier — пауза 4.5с):
  `facts_score` — доля эталонных подстрок в ответе; `refusal_ok` — для
  `out_of_scope` есть фраза отказа и нет `forbidden_facts`.
- Результат — JSON в `eval/results/` (коммитятся — это история качества).

**Baseline, 2026-09-05, 403 статьи AC:**

| метрика | значение | комментарий |
|---|---|---|
| recall@5 | **1.00** (26/26) | 22 из 26 — на rank 1 |
| MRR | 0.86 | |
| typo_fixed | 3/4 | не починился «Эцоо»: 4 буквы, триграммы на таких слабы |
| badfix | **2/27** | «Геральт → гера», «чемпионат → чемпиона» — см. раздел 11 |
| facts_score | 0.94 | |
| refusal_ok | **4/5** | провал — «Сколько статей?» → «Декларация ... 17 статей» |
| errors | 0 | |

Что показали числа, а не ощущения:

- **Retrieval на текущем корпусе — не проблема.** Единственный промах первого
  прогона оказался ошибкой датасета: эталон «Кто такой Робер де Сабле?» был из
  двух статей, а он описан в шести с лишком — retrieval вернул «Арсуф» и был прав.
  Урок: для сущностей без своей статьи эталон собирать поиском по корпусу.
- **Дистанции.** In-scope — 0.19–0.27 (24 из 26); сущности без своей статьи
  (де Сабле, храм Соломона) — 0.33; out_of_scope — 0.26–0.47. Пересечение
  реальное: «Сколько статей в базе по Assassin's Creed?» — **0.256**, глубоко в
  зоне нормальных вопросов, потому что содержит «Assassin's Creed». Вывод для
  порога — в разделе 11.
- **Генерация слабее поиска.** `narr-bayek-medjay`: обе половины нужного раздела
  в top-2 (0.19 и 0.23), модель ответила общими словами и добавила «в архивах нет
  информации», хотя история с Сабу и Бионом была перед ней. Поиск 100%, ответ —
  нет. Это и есть причина держать две метрики раздельно.
- **`facts_score` плавает на ±1 факт между прогонами** (temperature 0.1):
  «монголы» в ответе про смерть Альтаира то есть, то нет. `recall@5` не дрогнул
  ни разу — детерминирован по построению.

Известные ограничения раннера: `--full` считает эмбеддинг вопроса дважды (в
retrieval-части и внутри `execute`) и дублирует лог опечаток/rewrite — принято,
чтобы не менять `ChatUseCase` ради eval. Имя файла результата — с точностью до
минуты; два прогона с одной меткой в одну минуту перезапишут друг друга, поэтому
режимы помечаются разными метками (`baseline-retrieval` / `baseline-full`).

### Миграции — Alembic, не `create_all`

Схема версионируется через **Alembic** (`migrations/`), не голым
`Base.metadata.create_all` — тот умеет создавать отсутствующие таблицы, но не
добавляет колонки в существующие. Текущая голова: `a04d5680dde2` («add chunk
metadata columns, parent_chunk_id, jsonb»). Применение:

```bash
uv run alembic upgrade head
```

Миграция, среди прочего, добавляла `article_title`/`source_url` как `NOT NULL`
на уже населённую таблицу — автоген Alembic сгенерировал их сразу `NOT NULL`
без дефолта, что упало бы на существующих строках. Исправлено вручную: колонки
добавлены `NULLABLE`, бэкфилл через `UPDATE ... FROM articles`, затем
`ALTER COLUMN ... SET NOT NULL`.

*(Раздел 8 ниже описывает более ранний, до-Alembic способ добавления колонки —
пересозданием таблицы. Он больше не актуальный путь для этого проекта, но
описание оставлено как есть — исторически верно для момента, когда `is_proper`
появилась.)*

### Расширения

Установлены ровно два: `vector` 0.8.5 и `pg_trgm` 1.6.
Создаются при старте приложения в `lifespan`
([`main.py:16,19`](../main.py)) — до `create_all`, потому что на `lore_terms`
висит GiST-индекс с `gist_trgm_ops`.

`unaccent`, `fuzzystrmatch`, `btree_gist` доступны в образе, но **не установлены**
и не используются. Нормализация «ё → е» делается в Python — это дешевле и не
требует расширения.

### Индексы

| Таблица | Индекс | Тип |
|---|---|---|
| `articles` | `articles_pkey`, `articles_url_key` | btree, уникальные |
| `articles` | `ix_articles_title` | btree |
| `article_chunks` | `article_chunks_pkey` | btree |
| `article_chunks` | `ix_article_chunks_universe` | btree |
| `lore_terms` | `lore_terms_pkey`, `uq_lore_terms_article_term` | btree, уникальные |
| `lore_terms` | `ix_lore_terms_universe` | btree |
| `lore_terms` | `ix_lore_terms_term_trgm` | **GiST**, `gist_trgm_ops` |

**На `article_chunks.embedding` индекса нет.** Ни `IVFFlat`, ни `HNSW`.
Векторный поиск идёт последовательным сканом. **Текущий объём: AC 403 статьи /
2565 чанков, GTS 43 — 2608 чанков суммарно.** Первая версия документа
писала «заводить нужно, когда чанков станут тысячи, на нынешних 53 это было бы
преждевременно» — порог уже пройден: чанков тысячи. Индекс пока не заведён не
потому что рано, а потому что следующий шаг — HNSW должен строиться **после**
массовой заливки (bulk `CREATE INDEX` быстрее, чем инкрементальная поддержка
графа при построчной вставке), а полная заливка ещё не завершена (раздел 11).

`metadata_obj` — теперь `jsonb` (было `json`), но индекса на неё тоже нет:
в проекте ни одного запроса, фильтрующего по её содержимому, GIN добавляется
одной командой в момент, когда такой запрос появится — сейчас рано.

Индекс на `lore_terms.term` — именно **GiST**, а не GIN, и это принципиально:
GIN не поддерживает KNN-сортировку `ORDER BY term <-> 'слово'` и молча
вырождается в Seq Scan. Проверено на `EXPLAIN`.

## 7. RAG-конвейер

Что происходит внутри `ChatUseCase.execute`:

### Шаг 1. Исправление опечаток — Postgres, всегда, бесплатно

`correct_typos` ([`chat.py:53`](../app/use_cases/chat.py)) чинит опечатки
по словарю лора триграммами. Без вызова LLM. Разобрано в разделе 8.

### Шаг 2. Переписывание запроса — LLM, только при необходимости

```python
if _needs_llm_rewrite(corrected_question, history):
    rewritten_question = await self.llm_client.rewrite_query(...)
```

Условие ([`chat.py:58`](../app/use_cases/chat.py)): история непуста **и** в вопросе
есть местоимение. Только тогда есть что раскрывать — «а что он усовершенствовал?»
превращается в «Что Альтаир ибн Ла-Ахад усовершенствовал?».

Такое разделение экономит по вызову модели на каждом обычном вопросе и убирает
известную беду: на коротких запросах LLM-переписывание достраивает смысл наугад.
Реальный случай из лога — «Ориентация» превратилась в «Ориентация в пространстве»,
и ответ ушёл про физические координаты.

Температура переписывания — `0.0` ([`gemini_adapter.py:304`](../app/infrastructure/gemini_adapter.py)):
креатив тут вреден. Если вызов падает, возвращается исходный вопрос — вспомогательный
шаг не должен ронять весь запрос.

**Известный пробел этого шага** — история используется РОВНО здесь и нигде
больше: не в эмбеддинге, не в финальном промпте генерации. Разобрано в разделе 11.

### Шаг 3. Эмбеддинг — с защитой от сбоев Gemini

`generate_embedding` превращает текст в вектор из 768 чисел
(`gemini-embedding-001` по умолчанию отдаёт 3072, урезаем через
`output_dimensionality`). С сегодняшнего фикса ([`chat.py:73-84`](../app/use_cases/chat.py))
обёрнут в `try/except`: сбой (в том числе дневная квота Gemini) даёт пользователю
вежливое сообщение через стрим, а не необработанный traceback. Внутри — вся
устойчивость из раздела 5.3 (батчинг, троттлинг, различение дневного/минутного
лимита), общая с индексатором.

**Поиск асимметричный.** У метода есть параметр `task_type`, и он не косметика:
одно и то же слово с разным `task_type` даёт разные координаты.

| Что кодируем | `task_type` | Где |
|---|---|---|
| Чанк при загрузке | `RETRIEVAL_DOCUMENT` (по умолчанию) | `WikiChunker`/загрузчики |
| Вопрос при поиске | `RETRIEVAL_QUERY` | [`chat.py:75`](../app/use_cases/chat.py) |

Смысл в том, что вопрос и отвечающий на него абзац по словам обычно не похожи:
«Кто убил Альтаира?» и «Дорн нанёс смертельный удар» пересекаются разве что
именем. Модель обучена класть QUERY-вектор вопроса рядом с DOCUMENT-вектором
**отвечающего** куска, а не похожего по формулировке. Если кодировать обе стороны
как DOCUMENT, поиск вырождается в симметричный.

Побочный эффект, который пугает при первом взгляде: абсолютные расстояния в
QUERY-режиме **больше** (0.17 → 0.22 на тех же данных). Это не ухудшение —
значения из разных `task_type` несопоставимы в принципе, сравнивать можно только
порядок внутри одного режима.

Замер на корпусе GTS показал главный эффект: обтекаемый абзац без фактов в
симметричном режиме лежал близко ко всему подряд и занимал место в топ-5 у 8
вопросов из 12; в асимметричном — ни разу.

### Шаг 4. Поиск с предварительной фильтрацией

```python
distance = ArticleChunk.embedding.cosine_distance(qv).label("distance")
select(ArticleChunk, distance)
  .where(ArticleChunk.universe == universe)              # pre-filtering
  .order_by(ArticleChunk.embedding.cosine_distance(qv))  # KNN
  .limit(limit)
```

[`postgres_adapter.py:164-170`](../app/infrastructure/postgres_adapter.py).
Сначала отсекаем чужие вселенные, потом сортируем по косинусному расстоянию.
Это **metadata pre-filtering**: и быстрее, и не даёт смешаться разным вселенным.
Возвращается не только `chunk_text`, но и `article_title`/`section_path`/
`chunk_type`/`distance` — `ChatUseCase` из этого читает только текст, остальное
нужно eval-у (раздел 5.5) и будущему порогу релевантности.

Расстояние косинусное, то есть сравнивается **угол** между векторами, а не длина.
Поэтому длина исходного текста на близость не влияет.

### Шаг 5. Сборка контекста

Найденные куски склеиваются через `\n\n---\n\n`. Если не нашлось ничего —
подставляется заглушка «В архивах нет информации по этой теме». `distance`
найденных чанков теперь возвращается наружу, но **здесь не проверяется** — top-5
уходит в промпт, какой бы далёкой ни была лучшая находка. Раздел 11.

### Шаг 6. Генерация со стримингом

В модель уходит системная инструкция режима + контекст + **переписанный** вопрос.
Именно переписанный: отвечающая модель истории диалога не видит, и с исходным
«а сколько ему лет?» не поняла бы, о ком речь.

## 8. Исправление опечаток триграммами

Задача: пользователь пишет «Альтарир» вместо «Альтаир», поиск всё равно должен
находить нужное.

**Как работает.** `pg_trgm` режет слово на трёхбуквенные кусочки и считает долю
общих. Замеры на реальных данных:

| запрос | эталон | сходство |
|---|---|---|
| Альтарир | Альтаир | 0.545 |
| Альтаер | Альтаир | 0.455 |
| Исканедр | Искандер | 0.385 |
| Искандер | Альтаир | **0.000** |

Опечатки дают 0.38–0.70, разные слова — ровно ноль. Порог 0.35
([`postgres_adapter.py:23`](../app/infrastructure/postgres_adapter.py)) разделяет
их с запасом.

**Бонус:** пунктуация и регистр закрываются тем же механизмом бесплатно —
«Аль-Муалим» против «Аль Муалим» даёт 1.000.

**Словарь** наполняется автоматически в `save_chunks` из тех же чанков и чистится
каскадом при перезаливке статьи. Разовая пересборка — `rebuild_lexicon.py`
(LLM не вызывается, квота не тратится).

### Почему одних триграмм мало

Изначально ложные срабатывания отсекало единственное правило: слово, которое в
лоре есть, не трогаем; правим только незнакомые. На словаре из 177 слов этого
хватало. На 1670 словах — перестало: **13 запросов из 26 стали мутировать**.

```
«Что происходит при таймауте...»  ->  «Что проходит при таймаут...»
«Сколько раз он был женат?»       ->  «Сколько раз он был жена?»
«Какими протоколами пользуются»   ->  «какие протоколам используются»
```

Причина в том, что правило проверяло наличие слова **буквально**. В словаре лежат
«обработка», «обработке», «обработки», а в вопросе — «обработкой»; для проверки
это незнакомое слово, и триграммы услужливо подставляют ближайшую форму.

Поднять порог нельзя — замер разводит эти случаи в **обратную** сторону:

| пара | сходство |
|---|---|
| обработки / обработкой (падеж, ложное) | **0.615** |
| альтаир / альтарир (опечатка, нужное) | **0.545** |

Триграммы в принципе не отличают «другую форму слова» от «опечатки»: для них это
одна и та же дистанция.

### Две защиты, которые это чинят

**1. Знакомое слово определяется по основе.** Вместо точного совпадения —
`ts_lexize('russian_stem', ...)` с обеих сторон:

```
обработкой -> обработк     обработки -> обработк     совпало, не трогаем
альтарир   -> альтарир     альтаир   -> альтаир      не совпало, чиним
```

Латиница проходит стеммер насквозь (`mixvel → mixvel`), так что названия
поставщиков ведут себя как раньше. У стоп-слов `ts_lexize` возвращает пустой
массив — отсюда `COALESCE` до самого слова, иначе `NULL = NULL` даст «незнакомо».

**2. Заменой может стать только имя собственное** — колонка `is_proper`.
Латиница считается именем всегда (`Mixvel`, `error_source`), кириллица — только
если слово встречалось с заглавной буквы **не** в начале предложения и не капсом.
Флаг копится по ИЛИ по всем вхождениям: «Альтаир» в начале предложения выглядит
обычным словом, но хотя бы одно вхождение в середине выдаёт в нём имя.

Тонкость реализации: к тексту чанка приклеен заголовок раздела, поэтому границей
предложения считается ещё и перенос строки (проверять его надо **до** `rstrip()`,
иначе он этот перенос и съест), и цифра перед словом — «2.1 Технологический стек»
это нумерация, а не предложение с именем в середине.

**Результат:** мутирует 1 запрос из 26, и это `Альтарира → альтаир` — ровно то,
ради чего механизм и писался. Обратная проверка: `Mixvell`, `Sirna`, `Kafkaa`,
`Альтарир`, `Аль-Муаима` и смешанное `Исканder` чинятся; правильные написания не
трогаются.

### Производительность

| Сценарий | Время `correct_typos` |
|---|---|
| Обычный вопрос | 2.9 мс |
| Длинный вопрос, 10 слов | 6.6 мс |
| С опечаткой, доходит до KNN | 6.6 мс |
| Худший случай: 4 слова, ни одного знакомого | 14.4 мс |

Проверка по основе разворачивается в **один** hash semi join на весь запрос, а не
в скан на каждое слово. GiST-индекс после добавления фильтра `is_proper` не
сломался — `Index Scan ... Order By <->` на месте.

`ts_lexize` **нельзя проиндексировать**: функция `STABLE`, а функциональный индекс
требует `IMMUTABLE`. Поэтому проверка основ — линейный скан по словарю. На 1847
словах это 0.7 мс; упрётся в районе десятков тысяч терминов. Лечится колонкой
`term_stem`, заполняемой при вставке, и составным индексом с `is_proper` — сейчас
преждевременно, на таком объёме индекс проиграет скану.

Отдельный худший случай: `is_proper` применяется фильтром **поверх** обхода
индекса, а не сужает его. Слово, у которого похожих имён нет вообще, гонит KNN по
всему индексу до конца — 6.5 мс на слово. Такие запросы редки: после фикса
почти всё проходит как знакомое и до KNN не доходит.

**Историческая заметка (до Alembic).** Когда появлялась колонка `is_proper`,
миграций в проекте ещё не было — таблицы создавались через `create_all`, который
новые колонки в существующую таблицу не добавляет. `is_proper` тогда добавили
пересозданием:

```bash
docker exec lore_vector_db psql -U admin -d lore_db -c "DROP TABLE lore_terms CASCADE;"
uv run main.py                 # create_all поднимет таблицу с колонкой
uv run rebuild_lexicon.py      # словарь соберётся из chunk_text, без трат на LLM
```

Раздел 6 описывает актуальный способ (Alembic) — этот путь оставлен как
исторически верный на момент своего написания, не как текущая инструкция.

## 9. Режимы ответа

Стиль ответа выбирается в интерфейсе и **не привязан к вселенной**.

| Режим | Температура | Поведение |
|---|---|---|
| Рассказчик | 0.5 | живо и литературно |
| Архивариус | 0.1 | сухо, близко к тексту источника |

Промты и температуры лежат в словаре `_MODES`
([`gemini_adapter.py:135`](../app/infrastructure/gemini_adapter.py)),
сами режимы — в [`app/domain/answer_modes.py`](../app/domain/answer_modes.py).

**Как добавить третий режим:** дописать значение в `AnswerMode`, положить промт
и температуру в `_MODES`, добавить описание в `MODE_INFO`. Фронт подтянет кнопку
сам через `GET /api/v1/modes` — HTML трогать не нужно. При трёх и более режимах
вёрстка автоматически переключается с сегмента на вертикальный список.

В промте рассказчика граница вымысла проведена явно: украшать можно **язык**
(интонацию, ритм), но нельзя добавлять факты, события, имена, числа и даты.
Раньше правила противоречили друг другу — «делай литературно» против «ничего не
выдумывай» — и модель дорисовывала в ответ «неоновые огни», которых в источнике нет.

## 10. API и фронтенд

### Эндпоинты

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/v1/modes` | список стилей ответа |
| GET | `/api/v1/universes` | вселенные, по которым **реально есть данные** в БД |
| POST | `/api/v1/chat` | вопрос → потоковый ответ |

`/` отдаёт статику: `app.mount("/", StaticFiles(...))`
([`main.py:47`](../main.py)), смонтирована последней, чтобы не перехватывать `/api/v1/*`.

### Про «SSE»

У `StreamingResponse` стоит `media_type="text/event-stream"`
([`router.py:52`](../app/api/router.py)), но **настоящим SSE это не является**:
в потоке нет ни префиксов `data: `, ни разделителей `\n\n`. Это обычный
chunked-стрим сырого текста с SSE-подобным заголовком.

Фронт это подтверждает: он читает `res.body.getReader()`, а не `EventSource`.
`EventSource` с таким форматом не заработал бы.

Путаницы это не создаёт, но называть вещи стоит своими именами.

### Фронтенд

Один файл — [`static/index.html`](../static/index.html), без сборки.
Tailwind и Phosphor Icons с CDN.

Заметные решения:

- **Печать по времени, а не по кадрам.** Скорость задана в символах в секунду
  (`TYPE_CPS`), поэтому на 120-герцевом мониторе текст не набегает вдвое быстрее.
  Есть догон: если модель сильно убежала вперёд, печать ускоряется, иначе на
  длинных ответах копился бы хвост.
- **Оборванный стрим не притворяется ответом.** HTTP 200 уже отдан, статус
  задним числом не поменять — поэтому такой ответ помечается плашкой и **не
  сохраняется в историю**.
- **Состояние в localStorage.** Бэкенд stateless; история чатов, выбранная
  вселенная и режим живут в браузере.
- **Контраст.** Мелкий текст в сайдбаре поднят до `slate-400` (7.38:1).
  Прежний `slate-500` давал 3.98:1 — провал WCAG AA, где нужно 4.5:1.
- **История отправляется на бэкенд по-настоящему** ([`static/index.html:908-911`](../static/index.html)) —
  последние 6 сообщений, не пусто. Но см. раздел 11: бэкенд использует их узко.

## 11. Честные пробелы

Не потому что «забыли», а потому что на текущем объёме данных не нужно
(или потому что найдено сегодня и ещё не починено). Но знать про них стоит.

**Нет порога релевантности.** `search_similar` теперь отдаёт `distance`, но
`ChatUseCase` её не смотрит — в промпт всегда уходит top-5, каким бы далёким ни
было лучшее совпадение. Eval (раздел 5.5) дал распределение: in-scope 0.19–0.27
(24 из 26), сущности без своей статьи 0.33, out_of_scope 0.26–0.47. Чистого зазора
нет: «Сколько статей в базе по Assassin's Creed?» — 0.256, среди нормальных
вопросов. Порог ~0.30 отсёк бы 4 из 5 out_of_scope, но и 2 легитимных вопроса;
~0.35 безопасен для in-scope и ловит 3 из 5 (погода, футбол, Геральт). Вывод:
порог — необходимый, но недостаточный слой. Мета-вопросы про саму базу лежат
в зоне нормальных дистанций и требуют классификации intent (следующий пункт).

**Нет классификации intent (мета-вопрос vs вопрос по лору).** Тот же пример:
«Сколько статей?» — вопрос про саму систему, а не про лор, но бот всегда идёт
в retrieval, других веток нет. Возможный фикс — до похода в retrieval отвечать на
такие вопросы напрямую из `list_universes()`, тем же приёмом, что уже
используется для опечаток (детерминированная проверка перед LLM). Не сделано, но
теперь измеримо: eval-вопрос `oos-article-count` воспроизводит инцидент
детерминированно (top-1 — чанк главной страницы вики, 0.330; ответ — про
Декларацию). Фикс проверяется как рост `refusal_ok` с 4/5 до 5/5 без регрессий
`recall@5`.

**`correct_typos` ложно срабатывает на незнакомых словах.** Словарь имён вырос с
~1,7 тыс. до ~20 тыс. терминов вместе с Fandom-корпусом, и среди них — тысячи
коротких обрубков от разбиения дефисных имён («Эль-Какр» → «эль» + «какр»).
Триграммное сходство на коротких словах ненадёжно: триграмм мало, 2-3 общих
решают исход. Наблюдено: «какйо» (опечатка в «какой») → «какр» (0.375, чуть
выше порога 0.35), «Геральт» → «гера» (Гера из статьи «Аид»), «чемпионат» →
«чемпиона» («чемпиона» помечено именем из-за одной статьи «Альмогавары»). Eval
меряет это как `unexpected_correction`: 2 из 27 вопросов без опечатки изменены.
Разобранный, но **не применённый** фикс — вторая проверка по edit distance
(`≤ max(1, len // 3)`): ловит «какр» и «гера», не ломает «эцио» (4 буквы, но
настоящее имя — поэтому порог по длине термина отвергнут: он убил бы коррекцию
главного протагониста; в словаре 26% терминов короче 6 букв), **не ловит**
«чемпиона» — edit distance 1, это уже не про короткие слова, а про настоящее
слово, которого нет в корпусе. Решение отложено автором. Мерить: `badfix` → 0
при `typo_fixed` без падения.

**Чанкинг разного качества по вселенным.** Для AC (Fandom) — полноценный
structure-aware `WikiChunker`, раздел 5.2. Для GTS
([`load_gts.py`](../load_gts.py)) — чуть проще: заголовок раздела приклеен к
тексту, короткие пункты списков подклеены к предыдущему абзацу, но без overlap
и без рекурсивного сплита длинных секций. Первая версия документа описывала
это как общее свойство всего проекта — сейчас верно только для GTS. (Тестовая
вселенная Human с наивным `split('\n')` и ручная статья-образец про Альтаира
для AC удалены вместе со своими загрузчиками 2026-09-05: первая проекту не
нужна, вторая дублировала бы статью с Fandom.)

**Подсказки на пустом экране захардкожены во фронте.** Список вселенных приходит
из базы динамически, а карточки-подсказки лежат в объекте `SUGGESTIONS`
([`static/index.html`](../static/index.html)). Для новой вселенной их надо
дописывать руками, иначе экран будет пустым. Просится в ответ `/universes`.

**Нет векторного индекса.** См. раздел 6 — на нынешнем объёме (2608 чанков)
порог «пора заводить» уже пройден, HNSW откладывается намеренно до конца полной
заливки AC-корпуса (bulk `CREATE INDEX` дешевле инкрементальной поддержки графа
при построчной вставке), не потому что рано.

**Нет reranking, HyDE, query expansion.**

**История не доходит до генерации ответа.** Она используется только в
`rewrite_query`, и то — условно, только если в вопросе есть местоимение
([`chat.py:16-21`](../app/use_cases/chat.py)). Клиент шлёт 6 сообщений, сервер
использует последние 3 из них, и то не всегда. Бот не «помнит» разговор как
таковой — он лишь иногда понимает, о ком идёт речь, если явно спросили «а он...».
Вопрос без местоимения после смены темы («Сколько статей?» сразу после «Расскажи
про Эцио») историю не использует вообще, даже с полными данными на руках.

**Полная заливка AC-корпуса не завершена — и не только по времени.** На вики
2984 статьи, залито 403 (**13.5%**). Причины две, независимые:
1. **Дневная квота Gemini free tier** (~1000 запросов/день на `embed_content`) —
   штатное ограничение скорости, ждать полуночи по Тихоокеанскому и продолжать.
2. **Cloudflare-блокировка API Fandom** — обнаружена сегодня, не про Gemini
   вообще. `action=query`/`action=parse` начали отдавать 403 с телом
   `"Just a moment..."` (JS-challenge Cloudflare, `cf-mitigated: challenge` в
   заголовках). Ретраи `FandomScraper` тут принципиально бессильны — httpx не
   исполняет JS, никакое количество попыток проблему не решит. Похоже на
   репутацию конкретного (домашнего, динамического) IP у Cloudflare, а не на
   реакцию на наш объём трафика — с другого (рабочего, статического) IP всё
   работало без единой ошибки весь день. Копирование `cf_clearance`-cookie из
   браузера, прошедшего проверку с того же IP, не помогло — Cloudflare, похоже,
   смотрит и на TLS-отпечаток клиента, который у `httpx` отличается от
   настоящего браузера. Рабочий обходной путь — гонять индексатор с сети, где
   он уже отработал чисто; полноценное решение (реальный браузер через
   Playwright) сознательно не выбрано — несоразмерное усложнение ради временного
   неудобства.

**`_clean_wikitext` не знает про теги главной страницы.** Найдено тем же
диагностическим запросом, что и порог релевантности выше: чанк с
`"Assassin's Creed Wiki"` (сама вики, не статья) содержит необработанные
`<mainpage-leftcolumn-start/>`/`<mainpage-endcolumn />`. Список известных тегов
в `_clean_wikitext` покрывает `<ref>`/`<tabber>`, но не специфичные для главной
страницы layout-теги. Один такой чанк на весь корпус, не критично, но искажает
retrieval именно для мета-вопросов (см. пункт про классификацию intent выше —
тот самый чанк был в топ-3 по «Сколько статей?»).

**Нет начальной миграции.** Единственная ревизия `a04d5680dde2` имеет
`down_revision = None`, но начинается с `op.add_column('article_chunks', ...)` —
она предполагает таблицы, созданные `create_all` до появления Alembic. На пустой
базе `alembic upgrade head` упадёт. Обход — стартовать `main.py` (create_all),
затем `alembic stamp head`; описан в разделе 13 и README. Правильное лечение —
автогенерировать начальную ревизию с `create_table` и поставить её в
`down_revision` текущей, а `create_all` из `main.py` убрать, чтобы источник
схемы был один.

**Eval есть, но узкий.** 31 вопрос, только AC, эталоны — подстроки (с синонимами),
LLM-as-judge нет; `facts_score` плавает на ±1 факт между прогонами из-за
temperature 0.1. Достаточно, чтобы измерять retrieval и ловить регрессии;
недостаточно, чтобы судить о качестве формулировок ответа. Раздел 5.5.

**Каждое сообщение чата — минимум 2 вызова API** (эмбеддинг + генерация), а с
переписыванием три. На бесплатной квоте это ощутимо — раздел 5.3 показывает,
насколько буквально ощутимо.

## 12. Приложение: разбор документа Gemini

Документ-инвентаризация, составленный в отдельном чате при планировании, описывает
**не этот** проект. Ниже проверенные расхождения — важно, чтобы они не осели
в памяти как факты.

| Утверждение | Реальность |
|---|---|
| SDK `google-generativeai` | `google-genai` ≥2.14.0; старый пакет удалён |
| Драйвер `asyncpg` | `psycopg 3`; asyncpg не установлен |
| Используются `fuzzystrmatch` и `unaccent` | Не установлены. Только `pg_trgm` и `vector` |
| `temperature=0.7` | 0.5 / 0.1 по режимам, 0.0 для переписывания |
| Тег `[Вселенная: AC]` к чанкам | Не реализовано вообще |
| Режим «Все вселенные» | Не существует; вселенная всегда ровно одна |
| Стриминг через SSE | Заголовок SSE есть, формат — нет |
| UI в `client.html` | Файл называется `static/index.html` |
| Python 3.10+ | Требуется 3.12+, рантайм 3.12.13 |
| Переписывание «через LLM **или** pg_trgm» | Оба, по очереди: pg_trgm всегда, LLM условно |

Отдельно про `fuzzystrmatch`: даже если его установить, для русского из него
годится только `levenshtein`. `soundex` и `metaphone` на кириллице возвращают
**пустую строку для любого слова** — то есть формально «совпадают» все слова
со всеми. Проверено запросом в одноразовой базе.

Мораль, которая пригодится дальше: правдоподобный текст про архитектуру и
реальная архитектура — разные вещи. Сверяйтесь с кодом.

## 13. Запуск

```bash
docker compose up -d              # Postgres с pgvector
uv run alembic upgrade head       # накатить схему на СУЩЕСТВУЮЩУЮ базу (раздел 6)
# Пустая база: миграция a04d5680dde2 делает add_column и упадёт без таблиц.
# Один раз стартовать main.py (create_all создаст актуальную схему), Ctrl+C,
# затем `uv run alembic stamp head` — отметить схему как текущую.
uv run main.py                    # API + интерфейс на http://localhost:8000

# Вторая вселенная (разовая) и служебное:
uv run load_gts.py extract        # docx -> gts_chunks.json, без обращения к API (docx в репо нет)
uv run load_gts.py                # вселенная GTS из JSON
uv run rebuild_lexicon.py         # пересобрать словарь опечаток, без трат на LLM

# Основной источник AC — Fandom (раздел 5):
uv run index_fandom.py --dry-run --limit 5     # проверить чанкер, без LLM/БД
uv run index_fandom.py --limit 20              # малая реальная заливка
uv run index_fandom.py                          # весь корпус (часы, дневной лимит квоты)

# Eval — измерить качество на контрольных вопросах (раздел 5.5). Только как модуль:
uv run python -m eval.run_eval --validate                 # схема датасета + статьи есть в БД
uv run python -m eval.run_eval --label my-change          # retrieval-only, ~1 мин, ~35 embed-вызовов
uv run python -m eval.run_eval --full --label my-change   # + ответы ARCHIVIST, ~4 мин, ещё ~35 generate
uv run python -m eval.run_eval --compare eval/results/A.json eval/results/B.json
```

`load_gts.py` разбит на два шага намеренно: между ними текст правится руками.
В [`gts_chunks.json`](../gts_chunks.json) у каждого чанка два поля — `raw` как в
документе и `text` как уйдёт в базу; пустой `text` снимает чанк с загрузки, не
удаляя его из файла.

Ключ Gemini и строка подключения — в `.env`.
`url` в скриптах загрузки — ключ идемпотентности, менять его не нужно:
поменяете — получите дубль статьи вместо обновления. Для `index_fandom.py`
`url` строится автоматически из заголовка статьи Fandom, руками не задаётся.
