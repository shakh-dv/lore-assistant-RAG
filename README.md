# Lore Assistant

RAG-ассистент, отвечающий на вопросы строго по загруженной базе знаний. Вопрос
превращается в вектор, ближайшие куски текста достаются из Postgres и уходят в
Gemini как контекст — модель отвечает только по ним, без домыслов.

Архитектура — порты и адаптеры: бизнес-логика в `app/use_cases` не знает ни про
Gemini, ни про Postgres. Подробный разбор — в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Стек

Python 3.12 · FastAPI · SQLAlchemy (async) · PostgreSQL 16 + pgvector + pg_trgm ·
Gemini (`gemini-embedding-001` для векторов, `gemini-3.1-flash-lite` для ответов)

## Запуск

```bash
docker compose up -d                  # Postgres с pgvector на :5432
uv sync                               # зависимости
uv run python main.py                 # http://localhost:8000
```

В `.env` нужны две переменные:

```
GEMINI_API_KEY=...
DATABASE_URL=postgresql+psycopg://admin:secretpassword@localhost:5432/lore_db
```

Таблицы и расширения создаются сами при старте, вручную ничего накатывать не надо.

## Загрузка данных

База пустая — ассистенту нечего отвечать. Загрузчики:

| Команда | Что грузит |
|---|---|
| `uv run python load_lore.py` | вселенная `AC` — статья про Альтаира |
| `uv run python load_human.py` | вселенная `Human` — карточка персонажа |
| `uv run python load_gts.py extract` | `.docx` → `gts_chunks.json` (без обращения к API) |
| `uv run python load_gts.py` | вселенная `GTS` — база знаний из JSON |
| `uv run python rebuild_lexicon.py` | пересборка словаря опечаток из уже залитых чанков |

Вселенные подхватываются интерфейсом автоматически — список берётся из базы.
А вот карточки-подсказки на пустом экране захардкожены во фронте
([`static/index.html`](static/index.html), объект `SUGGESTIONS`): для новой
вселенной их нужно дописать руками, иначе экран будет пустым.


# Что менялось в этой итерации

Четыре независимых блока работ. Ниже — что именно и зачем.

## 1. Асимметричные эмбеддинги: вопрос и документ кодируются по-разному

**Было:** `task_type` был захардкожен в `RETRIEVAL_DOCUMENT`, поэтому вопрос
пользователя кодировался как ещё один абзац базы. Поиск получался симметричным:
искался кусок, **похожий на вопрос**, а не **отвечающий** на него.

**Стало:** `task_type` стал параметром. Загрузчики кодируют чанки как
`RETRIEVAL_DOCUMENT` (значение по умолчанию), `ChatUseCase` кодирует вопрос как
`RETRIEVAL_QUERY`. Переиндексация не требуется: база лежит в DOCUMENT-пространстве,
QUERY-векторы целятся именно туда.

**Тронуто:** [`app/domain/ports.py`](app/domain/ports.py) ·
[`app/infrastructure/gemini_adapter.py`](app/infrastructure/gemini_adapter.py) ·
[`app/use_cases/chat.py`](app/use_cases/chat.py)

**Замер на корпусе GTS (44 чанка, 12 вопросов).** Главный эффект — исчез
чанк-паразит: обтекаемый абзац без фактов («Работа строилась поэтапно...») в
симметричном режиме лежал близко ко всему подряд и занимал место в топ-5 у **8
вопросов из 12**, съедая пятую часть контекста. В QUERY-режиме — **0 из 12**.
Топ-1 сменился в 3 вопросах: два в лучшую сторону, один сместился на строку вниз.

## 2. База знаний о платформе GTS из отчёта по практике

**Добавлено:** [`load_gts.py`](load_gts.py) — загрузчик `.docx` на stdlib
(`zipfile` + `ElementTree`), без новых зависимостей. Работает в два шага, потому
что между ними текст правится руками:

```bash
uv run python load_gts.py extract   # docx -> gts_chunks.json
uv run python load_gts.py           # gts_chunks.json -> база
```

В [`gts_chunks.json`](gts_chunks.json) у каждого чанка два поля: `raw` — как в
документе, `text` — что уходит в базу. Пустой `text` снимает чанк с загрузки, не
удаляя его из файла: видно, что абзац рассмотрели и признали бесполезным, а не
потеряли.

**Что отфильтровано.** Разделы 5–7 и заключение — рефлексия о самой практике
(«чему я научился»), в базу знаний о платформе они не идут; управляется константой
`KEEP_SECTIONS`. Из оставшихся 44 чанков 28 переписаны из первого лица в стиль
справочника, 15 оставлены как есть, 1 снят с загрузки. Первое лицо: было 24 чанка
из 44, стало 0 из 43. Все названия, версии и термины сохранены — сверялось
автоматически по якорям (латиница, числа, версии).

**Тронуто:** [`static/index.html`](static/index.html) — четыре карточки-подсказки
для вселенной `GTS`.

## 3. Корректор опечаток перестал ломать нормальные запросы

**Было:** `correct_typos` правил любое слово от 4 букв, которого нет в словаре
буквально. А словарь набирался из **всех** слов корпуса подряд, включая глаголы и
местоимения. На словаре в 1670 слов это давало `происходит → проходит`,
`женат → жена`, `пользуются → используются` — **13 запросов из 26 мутировали**.

Поднять порог сходства было нельзя: у падежной формы сходство **0.615**, у
настоящей опечатки — **0.545**. Триграммы в принципе не отличают «другую форму
слова» от «опечатки».

**Стало:** две независимые защиты.

1. **Знакомое слово определяется по основе**, а не буквально — через
   `ts_lexize('russian_stem', ...)`. «обработкой» и «обработки» дают общую основу
   «обработк», слово считается знакомым и не трогается. У настоящей опечатки
   основа своя: «альтарир» ≠ «альтаир».
2. **Заменой может стать только имя собственное.** У термина появился флаг
   `is_proper`: латиница — всегда имя (`Mixvel`, `error_source`), кириллица —
   только если слово встречалось с заглавной буквы не в начале предложения и не
   капсом. Теперь «убить» просто не может быть кандидатом на замену.

**Тронуто:** [`app/infrastructure/database/models.py`](app/infrastructure/database/models.py)
(колонка `is_proper`) ·
[`app/infrastructure/postgres_adapter.py`](app/infrastructure/postgres_adapter.py)
(`extract_terms` отдаёт `{слово: имя}`, `_save_terms` копит флаг по ИЛИ через
`on_conflict_do_update`, `correct_typos` получил обе защиты) ·
[`rebuild_lexicon.py`](rebuild_lexicon.py)

**Результат:** мутирует **1 запрос из 26** — и это `Альтарира → альтаир`, ровно
то, ради чего механизм и писался. Обратная проверка: 6 подсунутых опечаток
(`Mixvell`, `Sirna`, `Kafkaa`, `Альтарир`, `Аль-Муаима`, смешанное `Исканder`)
чинятся, 4 правильных написания не тронуты.

**Миграции нет.** Схема создаётся через `create_all`, который новые колонки в
существующую таблицу не добавляет. Таблица `lore_terms` пересоздаётся:

```bash
docker exec lore_vector_db psql -U admin -d lore_db -c "DROP TABLE lore_terms CASCADE;"
uv run python main.py          # create_all поднимет таблицу с новой колонкой
uv run python rebuild_lexicon.py
```

Эмбеддинги при этом не трогаются — словарь собирается из уже лежащего в базе
`chunk_text`, квота не тратится.

## 4. Производительность корректора

Проверялось, не стал ли `ts_lexize` (его нельзя проиндексировать: функция
`STABLE`, а функциональный индекс требует `IMMUTABLE`) узким местом.

| Сценарий | Время |
|---|---|
| Обычный вопрос | 2.9 мс |
| Длинный вопрос, 10 слов | 6.6 мс |
| С опечаткой, доходит до KNN | 6.6 мс |
| Худший случай: 4 слова, ни одного знакомого | 14.4 мс |

Проверка по основе разворачивается в **один** hash semi join на весь запрос, а не
в скан на каждое слово. GiST-индекс после добавления фильтра `is_proper` не
сломался — `Index Scan ... Order By <->` на месте.

Обе операции линейны по размеру словаря (сейчас 1847 слов). Упрётся это в районе
**десятков тысяч** терминов; лечится колонкой `term_stem`, заполняемой при вставке,
и составным индексом с `is_proper`. Сейчас преждевременно: на таком объёме индекс
проиграет скану.

## 5. Техническая опись приведена в соответствие

[`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) описывал состояние до этих правок,
местами прямо противоречащее коду. Вычитан:

- **§5 «Таблицы»** — описана колонка `is_proper`.
- **§5 «Индексы»** — «при десяти чанках» заменено на актуальные 53.
- **§6 «Шаг 3. Эмбеддинг»** — добавлен разбор асимметричного поиска: таблица
  `task_type` по сторонам, зачем это нужно и почему расстояния в QUERY-режиме
  выросли, хотя качество не упало.
- **§7** — переписан. Утверждение «слово, которое в лоре есть, не трогается
  никогда, поэтому ложных срабатываний нет» было ровно тем багом, что описан в
  пункте 3. Теперь там разобрано, почему одних триграмм мало, обе защиты и замеры
  производительности.
- **§10 «Честные пробелы»** — `task_type` убран из списка нерешённого (закрыт);
  добавлены захардкоженные во фронте подсказки.
- **§12 «Запуск»** — добавлены `load_human.py` и оба шага `load_gts.py`.
